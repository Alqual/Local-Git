# Self-RAG リポジトリの局所性（Locality）評価レポート

本レポートは、今回の検証対象である `Self-RAG` のサンプルリポジトリが、他の一般的なRAG（Retrieval-Augmented Generation）用コードベース（例: LangChain, LlamaIndex等のエコシステム）と比較してどのような「局所性（独自性・特異な依存関係）」を持っているかを評価・分析したものです。

---

## 1. 局所性（Locality）の核心：APIエコシステムか、ローカルGPUエコシステムか

最も大きな違いは、通常の実用向けRAGコードベースが「**API（部品）の糊付け**」として抽象度高く設計されているのに対し、Self-RAGのコードベースは「**ハードウェア（GPU）とモデルアーキテクチャへの密結合**」を前提としている点にあります。

### 一般的なRAGレポジトリの特性
- **モジュラー性（高）**: 言語モデル（OpenAI API等）、ベクトルDB（Pinecone等）、検索アルゴリズムが完全に分離されており、容易に交換可能です。
- **インフラ非依存**: 推論や検索はすべてクラウドのAPI側で行われるため、実行環境は数MBのメモリとCPUがあれば動作します。

### Self-RAGレポジトリの局所性
- **モノリシックな密結合**: Self-RAGは、単にプロンプトで外部APIを制御するのではなく、**Llama-2などのオープンモデルの中身（重み）に直接介入**し、特殊な自己評価トークン（`[Retrieval]`, `[Relevant]` 等）の生成確率を直接操作するアルゴリズムを核としています。
- **推論エンジンの内包**: 外部APIを呼ぶのではなく、リポジトリ自体が `vLLM` を用いて「自分自身のローカルGPU上でLLMをホスティングし、トークン単位で計算を管理する」ことを前提としてハードコードされています。

---

## 2. 局所性がもたらす実装上の違いと具体例

### A. 依存ライブラリの極端な硬直性（バージョンのロックイン）
一般的なRAGが `pip install langchain openai` といった最新ライブラリの追従を許容する一方で、Self-RAGは極めて強いバージョンロック（局所性）を持ちます。
- **事実**: Tier 1検証時、ベースラインスクリプト (`run_baseline_lm.py`) が `openai` パッケージのv1.0.0系ではなく、廃止された専用の例外クラス (`openai.error.APIError`) にハードコード依存していました。
- **影響**: リポジトリが記述された時点（2023年末）の特定のパッケージバージョン (`openai==0.28.1`) へのダウングレードを強制され、最新の汎用システムとは共存できない隔離されたPython環境（`venv`）を必要とします。

### B. 重装備なCUDA拡張ライブラリの強制
- **事実**: `requirements.txt` には `vllm==0.2.6`, `deepspeed==0.12.6`, `flash-attn==2.3.6` といった、コンパイル時に特定のNVIDIAドライバ（CUDA CUDA Toolkit）を強烈に要求するライブラリが含まれています。
- **影響**: 対象環境（VRAM 6GB）など、特定スペックを満たさない一般的なローカルPCや、OSの標準状態ではセットアップスクリプトが必ずコンパイルエラーを起こします。「誰もがどこでも動かせるコード」機動性はなく、「大規模GPUクラスタ」環境に局所化されています。

### C. 検索・入力インターフェースの非汎用性
- **事実**: 一般的なRAGではPDFやWeb直読みなどのローダーが標準装備されますが、Self-RAGの `passage_retrieval.py` は、完全に事前処理された `TSV` コーパスと、Faissインデックスによる専用のエンベディング形式（Pythonの `pickle` でシリアライズされたNumpy行列）の読み込みに限定されています。
- **影響**: 外部データベースとの動的な通信ではなく、前処理された静的ファイル群（バッチ処理）のI/Oに最適化されており、バッチ実験用のコードとしての局所性が非常に高いです。

## 3. 環境準備やテスト検討において必要な考慮事項

このような「局所性の高いリポジトリ」を扱う際、環境構築やテスト計画において決定的に重要な考慮事項は以下の3点です。

### ① 「フルセットアップ」を避け、「部分結合（DI分離）」を計画すること
公式の `requirements.txt` をそのまま実行すると失敗します。今回我々が取ったアプローチのように、「検索モジュールだけ（PyTorch + FAISS）」「API評価モジュールだけ（OpenAIダウングレード版）」というように、**コードを機能単位で隔離し、動作に必要な最小ライブラリだけを手動選定してインストールする（依存環境のデカップリング）** 必要があります。

### ② ダミーデータによる「I/Oアーキテクチャのみ」の先行検証
膨大な計算コストを要求するモデル（Llama-2等）をダウンロード・稼働させる前に、今回用いた `dummy_corpus.tsv` のような**軽量なモックテキストを用いて、スクリプトの入出力形式（JSONL等のデータフローパース）が動作するかを先行テスト**しなければなりません。データ形式のハードコード（局所性）が強いため、フォーマットエラーで計算資源を無駄にすることを防ぎます。

### ③ クラスやAPIのモック化（Tier 2 アプローチの必要性）
推論エンジンに `vLLM` がハードコードされている以上、制約のあるハードウェア（VRAM 6GB）でリポジトリの全貌をテストするには、**ソースコード上でLLMを初期化しているクラスを「固定の返答を返すFakeクラス」に置き換える（Mocking）などのハック**が不可避となります。これが、抽象度の高いコードベースとの決定的なテスト難易度の違いとなります。

# SOTA AI Agents: アーキテクチャ別「無損失（Lossless）技術」深掘り技術レポート

現在のトップエージェントたちが、『内部のLLMの忘却』を防ぐために具体的に **どのようなコード構造・ライブラリ** を用いているか、またそれらが抱える **現在の重篤な技術的課題（無損失層構築への障壁）** と **参照リポジトリ** について深掘りします。

---

## 1. Manus / OpenHands系 (CodeActアーキテクチャ)
JSONによるAPIコールに依存せず、「推論結果を直接実行可能なPythonコードとして出力させ、SandBox環境で実行・評価する（Code-as-Action）」パラダイムです。

- **コア技術**: `Jupyter Kernel`, `subprocess.Popen` (Docker内隔離)
- **無損失実装**: Python実行結果の `STDOUT` (標準出力) や `STDERR` (スタックトレース) を絶対的な事実として捉え、次のターンの入力にLosslessに結合します。
- **現在の課題 (無損失層への障壁)**:
  1. **出力の暴走 (Log Overflow)**: スクリプトが巨大な配列やログを出力した場合、数十万トークンとなってコンテキストが破壊されます。
  2. **不可逆な状態変更のエラー (Irreversible State)**: `$ rm -rf /` のような破壊的操作やAPIの誤送信を実行してしまった場合、デジタルなテキストのように「Undo（巻き戻し）」が効きません。外部ステートの物理的破損にモデルが対応できません。
  3. **沈黙のエラー (Silent Failures)**: Pythonの実行ステータスが `exit 0`（成功）であっても、「論理的には間違っている（期待した計算をしていない）」場合があります。エラーが出ないため、エージェントは「成功した」という間違った記憶を無損失層に刻み込み、破綻が連鎖します。
  4. **揮発性メモリ問題**: Jupyter Kernelがクラッシュした場合、それまでのメモリ空間（変数やオブジェクト）が全て吹き飛びます。すべての変数をシリアライズしてディスクに保存していない限り、本当の意味でのLosslessにはなりません。
- **代表的なリポジトリ**: [OpenHands/OpenHands](https://github.com/OpenHands/OpenHands)

## 2. AutoGLM / AutoClaw系 (ローカル&ブラウザエージェント)
スクリーンショットのピクセル処理に頼らず、「ブラウザの階層構造（DOM）に直接アクセス」することで状態遷移を確定的（Lossless）に制御します。

- **コア技術**: `Playwright` / `Puppeteer`, `Chrome DevTools Protocol (CDP)`
- **無損失実装**: Playwrightで取得したDOMツリーをフィルタリングし、「連番付きのインタラクティブ・ノード」としてLLMに渡し、システム側で確実に対応するXPath等にマッピングし絶対座標で物理クリックさせます。
- **現在の課題 (無損失層への障壁)**:
  1. **動的DOMの崩壊 (Dynamic Web)**: SPA（React等）では画面遷移なしでDOM構造が1秒単位で書き換わります。「さっきまで存在した要素番号」が消滅・乱数化され、次の瞬間には使えないゴミデータ（Lossy）になります。
  2. **シャドウDOM / iFrameの壁**: WebGL上の描画、外部決済ウィジェット（iFrame）、悪意あるボット対策の画像認証など、DOMツリー（解析機）から意図的に隠蔽された領域には物理的にアクセスできません。
  3. **マウスオーバー等の隠しイベント**: Hover（カーソルを重ねる）しないと出現しないメニューや、CSSの擬似要素はDOMツリーの初期状態には完全記載されていないため、構造全体の情報をLosslessに取得することが仕組み上不可能です。
  4. **トークンの肥大化**: いくら不要なノードを削っても、Amazonなどの複雑なページは数万トークンのDOM文字列になります。これを毎ターンLLMに読ませると、推論の精度（Attention）が著しく低下します。
- **代表的なリポジトリ**: [zai-org/Open-AutoGLM](https://github.com/zai-org/Open-AutoGLM)

## 3. Claude (Anthropic: Computer Use API)
OSレベルのデスクトップ操作において、XML形式の厳格なタグ付けと、ネイティブ操作コマンドを直結させる技術です。

- **コア技術**: `xdotool` (Linux向けGUI操作), `JSON Schema`
- **無損失実装**: Claudeが厳密な JSON Schema に従った座標引数を出力し、外側のLinuxシステムがそれを `xdotool` 等のOSネイティブコマンドに変換して実行。ステータスコードを再度入力させます。
- **現在の課題 (無損失層への障壁)**:
  1. **非同期の盲目性（Blind Execution）**: `xdotool` は指定された座標を無慈悲にクリックしますが、OSは「そこにボタンがあったか」を返してくれません。通信ラグで対象アプリの起動が遅れた場合、全く無関係のファイルを削除するなどの大惨事（空振り）を起こします。
  2. **座標のドリフト（画面の脆さ）**: 画面の解像度が変更されたり、OSの通知ポップアップが画面上部に出現してウィンドウ全体が50px下にズレただけで、LLMが計算した全ての絶対座標が狂います。
  3. **画像のコンテキストコスト**: 確実性を担保するためには、毎回のクリック後にスクリーンショット（数千トークンの画像データ）をLLMに再送信し続ける必要があり、コストの爆発と処理速度の激しい低下を招きます。
  4. **フォーカスの喪失**: 「Ctrl+C」などのキーボード送信時、意図したウィンドウにフォーカスが当たっていない場合、最悪ユーザーの公開チャット等にパスワードが流出する危険性を常に孕んでいます。
- **代表的なリポジトリ**: [anthropics/claude-quickstarts/tree/main/computer-use-demo](https://github.com/anthropics/claude-quickstarts/tree/main/computer-use-demo)

## 4. Antigravity (DeepMind Agentic アプローチ)
IDE（ローカル開発環境）とハイブリッドに結合したファイルベースの状態管理を行います。（私自身に近似のアーキテクチャ）

- **コア技術**: Function Calling API, AST（抽象構文木）構文解析, OSファイルシステム連携 (`grep_search`等)
- **無損失実装**: 計画や状態を即座に `task.md` などの物理ファイル（アーティファクト）としてユーザーのディスクに永続化し、最新のステートをファイルシステムという「劣化しない外部データベース」から読み戻します。
- **現在の課題 (無損失層への障壁)**:
  1. **環境同期の競合 (Race Conditions)**: ユーザー（人間）とエージェントが同じファイルを同時に編集した場合、Losslessであるはずのファイル情報にコンクリフト（矛盾）が生じ、エージェントの記憶と現実が乖離します。
  2. **AST解析の崩壊**: エージェント自身が途中でSyntax（構文）エラーのあるコードを書き込んでしまった場合、構文解析器（AST Parser）が機能停止に陥り、情報が抽出できない全盲状態になります。
  3. **意図（セマンティクス）の忘却**: 物理ファイルは文字をLosslessに保持しますが、「なぜ昨日このコードを書いたのか」という設計思想（意図）はディスク上には残りません。
  4. **I/Oコスト**: 巨大なコードベースの最新情報をLosslessに保つため、毎ターン数百KBのファイルを読み直してLLMに読ませる「コンテキストのI/O税」が極めて高くつきます。

---

### まとめ（根本的なパラドックス）
各エージェントが無損失（Lossless）層を確立しようとしていますが、直面している課題の共通点は**「LLMの出力と、現実の物理的レイテンシ/ダイナミズムとの乖離」**です。

アーキテクチャの制御系統をどれほどLosslessにしても、その外側の「対象システム（OS, ブラウザ, DB）」自体が常に変化（Lossy）し続けているため、**『Losslessな制御情報を現実に投影した瞬間にエラーが起きる』**という強烈なパラドックスが現在の最大級の課題となっています。

# Self-RAG レポジトリ上の制約と実行可能実験の保証範囲 (v2: 保証可能性の技術規格検証)

本ドキュメントは、Self-RAGの公式リポジトリ（無改造のコード群）において、どのスケール・モデル・環境であれば確実に実験が可能か（保証されるか）を、コードのアーキテクチャ構造とハードウェア制約に基づき厳密に評価した結果です。

## 1. 提案した実験方針に対する「保証可能性」の結論と技術的詳細

先にお示しした各検証候補について、リポジトリのコードに基づく実際の実行可否と、それ（保証の有無）を決定づけている技術的背景・規格的理由を詳細に解説します。
結論として、**候補1および候補2については、そのままのコードで実行することは保証できません（コードの改変・ハックが必須となります）。**

### 1.1 候補1: Mock LLMによるシミュレーション（❌ 不可 / 要改造）
* **概要**: 推論モデルそのものをダミー（Mock）に差し替え、I/O処理のパイプラインだけを実行するテスト。
* **Mock オブジェクトの機能と規格とは**: 
  一般的にMock（モック）とは、依存性の注入（Dependency Injection: DI）といった規格・設計パターンを用いて、外部から「本物のモデル」と「テスト用のモックモデル」を柔軟に切り替えられるようにする仕組みです。
* **保証されない技術的理由**:
  Self-RAGリポジトリの推論スクリプトは、**依存性の注入機構（DIインターフェース）を備えていません。** `Hugging Face` の特定のクラスをハードコーディングしているため、実行するにはソースコード上の初期化部分を直接エディタでMockクラスに書き換えるというハッキングが必要になります。

### 1.2 候補2: 極小規模モデル(TinyLlama等)の代用（❌ 不可 / 要改造）
* **概要**: 高VRAMを要求される公式7Bモデルの代わりに、動作の軽い小規模LLMをそのままRAGシステムに投入するテスト。
* **トークンとボキャブラリ（語彙）の規格とは**:
  Self-RAGは学習時に通常の文字とは別に、`[Relevant]` 等の文字列をそれぞれ「1つの独立した特殊トークン」としてボキャブラリにハード登録しています。
* **保証されない技術的理由**:
  小規模な事前学習済みモデルのトークナイザ（辞書）には、これらの特殊トークンが含まれていません。スクリプトが辞書に問い合わせた際に未知トークン `<unk>` が返却され、確率分布配列（Logitsテンソル）から特定のインデックスを抽出する数学的な計算ステップにおいて、不正なID参照が発生してプログラムが必ずクラッシュします。

### 1.3 候補3: 検索エンジン(Contriever)単体の稼働テスト（✅ 実行保証）
* **アーキテクチャの疎結合性と保証される技術的理由**:
  `retrieval_lm/passage_retrieval.py` のアーキテクチャは、LLM（Generator）のコードから完全に疎結合化されています。ユーザー環境の6GB VRAMにおいてもモデルテンソルに十ニ分なメモリマージンがあり、公式スクリプトを一切改変せずに確実に動作させることが保証されます。

## 2. どのスケール・モデル・環境で全機能の実験が「保証」されているか

* **対象モデル規格 (Generator)**: `meta-llama/Llama-2-7b-hf` または `13b` ベースのみ（他モデル非サポート）。
* **ハードウェアスケール規格**: 最低 **14GB〜16GB** (Short-form)、**24GB〜** (Long-form/適応的検索)
* **対象モデル規格 (Retriever)**: `facebook/contriever-msmarco` (VRAM 2〜4GB で動作可)

---

## 3. 現状保証の条件下において取り得る「無改造の実験シナリオ」

以上のハードウェア制約(VRAM 6GB)上、コード改変なしで安全・確実に実行を行える実験テーマは以下の2つに限定されます。

1. **実験A: Contriever によるベクトル検索構築・情報抽出パイプラインの検証** (`passage_retrieval.py` を使用)
2. **実験B: OpenAI APIベースラインを用いた QA推論評価の検証** (`run_baseline_lm.py` を使用)

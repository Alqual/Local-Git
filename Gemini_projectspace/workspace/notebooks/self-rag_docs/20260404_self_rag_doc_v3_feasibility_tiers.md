# Self-RAG 実験環境構築と実現可能性の3段階評価 (v3: 許容工数とハードウェア制約に基づく階層化)

本ドキュメントは、ユーザーの「VRAM 6GBのマシン」という物理的制約と、「コード改変のタイムラグを許容するか」という観点に基づき、Self-RAGリポジトリを用いた実験可能性を3段階のTier（階層）に再分類した最終提案版です。

## Tier 3: 改造しても解決が不可（ハードウェアの絶対的限界）

どれほどソースコードを書き換えても物理的なGPUメモリ(6GB)が足りないため、実行できないテスト群です。

* **❌ 候補A: 公式7B/13Bモデルを用いたSelf-RAG推論・学習のフル稼働**
  * `meta-llama/Llama-2-7b-hf` モデルはFP16でロードするだけで約14GBのVRAMを消費します。量子化（4-bit等）を駆使してロードしても、複数文書をコンテキストとして読み込む推論時のKVキャッシュ計算で確実に VRAM Out Of Memory (OOM) となります。

---

## Tier 2: 改造（コード書き換えのタイムラグ）により解決が可

無改造ではエラーで落ちますが、**ソースコードの改変（ハック）を行う時間さえ担保できれば実行可能となる** 自由度の高い実験群です。

* **⚠️ 候補B: Mock LLMクラス実装による推論アルゴリズム模擬結合（DIハック）**
  * `run_long_form_static.py` のモデル初期化部分を「予め決められた文字列（特殊トークン入り）を含む出力を返すFakeクラス」で丸ごと置換します。ビームサーチ内の確率スコア重み付けの計算フロー等のシステム内部をシミュレートできます。
* **⚠️ 候補C: 極小LLM(TinyLlama等)の特殊トークン拡張・推論ハック**
  * モデルのHugging Faceトークナイザに特殊トークンを無理やり追加するか、またはソースコード上でターゲットトークンをダミー（例: `Yes`）にマッピングし直す処置を施します。「実際に稼働する推論グラフ上で、RAG検索結果がどう生成部に食わされるか」の極限挙動テストがVRAM 2GB程度で可能になります。
* **⚠️ 候補D: API（OpenAI等）をSelf-RAG推論エンジンとして組み込む機能ハック**
  * 公式のBaselineコードではなく、`run_long_form_static.py` 本体を改造します。モデルがLogitsを返す部分で外部APIにアクセスさせ、確率判定を無理やりAPIに代行させてSelf-RAGのビームサーチエンジンを回す検証です。

---

## Tier 1: 無改造でそのまま実行可（公式にサポートされた機能）

VRAM 6GB環境下において、リポジトリをダウンロードした状態で公式ガイドに沿ってそのまま動作させることが保証されている実験です。

* **✅ 候補E: 検索コンポーネント (Contriever) 単体の稼働テスト**
  * `passage_retrieval.py` による情報の検索・抽出部分。クエリからFAISSインデックス探索を経てJSONL出力されるまでの、RAGシステム前半の純粋なデータI/Oを検証します。
* **✅ 候補F: ベースラインスクリプトとAPIを用いた標準QA評価パイプライン実行**
  * `run_baseline_lm.py` による情報評価フェーズ部分。APIを使って結果を出し、`metrics.py` による正解一致率（Exact Match, F1 Score）の計算ロジックがどう動作するかを検証します。
